## Part 1. 논문이란 무엇인가

### 논문의 네 가지 특징
- **문제의식에서 출발**: 현상이나 필요에 대한 질문에서 글이 시작됨
- **근거 기반 주장**: 데이터, 실험, 구현 결과로 주장을 뒷받침
- **논리적 전개**: 서론 → 방법 → 결과 → 논의로 이어지는 인과적 흐름
- **재현 가능성**: 다른 사람이 같은 과정을 따라가도 같은 결론에 도달해야 함

### 논문 vs 보고서·에세이

| 항목 | 보고서·에세이 | 논문 |
|---|---|---|
| 목적 | 정보 전달·의견 표현 | 주장의 논증과 검증 |
| 근거 | 개인 경험·의견 위주 | 데이터·실험·선행연구 기반 |
| 구조 | 비교적 자유로운 형식 | IMRaD 등 정형화된 구조 |
| 평가 기준 | 가독성·설득력 | 독창성·논리성·재현 가능성 |

### 논문의 종류
- **학술논문**: 학술지·학회에 게재하는 연구논문
- **학위논문**: 졸업을 위한 석·박사 논문
- **프로젝트(캡스톤) 논문**: 오늘 다루는 실습 대상

### 좋은 논문의 조건
- **독창성**: 나만의 관점이나 접근이 있는가
- **논리적 일관성**: 주장과 근거가 어긋나지 않는가
- **재현 가능성**: 과정을 따라가면 같은 결론에 도달하는가

## Part 2. 논문의 기본 구조 (IMRaD)

```
서론(Introduction) → 방법(Methods) → 결과(Results) → 논의(Discussion)
```

> 초록(Abstract)과 키워드는 이 네 단계를 압축해 미리 보여주는 요약이다.

### 서론에 담을 내용
- 연구 배경 — 왜 이 주제인가
- 문제 정의 — 무엇이 문제인가
- 연구 목적·질문 — 무엇을 밝히려 하는가
- 논문 구성 안내 — 이후 어떤 순서로 읽히는가

### 방법에 담을 내용
- 연구·개발 절차 — 어떤 단계를 거쳤는가
- 사용 기술·도구 — 무엇으로 구현했는가
- 실험·평가 설계 — 무엇을, 어떻게 측정했는가
- 데이터 수집 방법 — 데이터는 어디서 왔는가

### 결과에 담을 내용
- 정량적 데이터 — 측정값, 수치, 통계
- 표·그래프 — 비교와 추이를 보여주는 시각자료
- 비교 분석 — 기존 방식과의 차이

### 논의에 담을 내용
- 결과 해석 — 그래서 무엇을 의미하는가
- 연구 의의 — 무엇을 기여했는가
- 한계와 향후 과제 — 무엇이 부족했는가

> 두 섹션(서론/방법, 결과/논의) 모두 프로젝트 발표 때 다뤘던 내용을 그대로 옮기면 되며, 순서와 표현만 논문식으로 바꾸면 된다.

## Part 3. 프로젝트를 논문으로

> 핵심: **"왜 만들었는가"를 "왜 필요했는가"로 바꾸는 것부터 시작**한다.

### 프로젝트의 동기를 연구 배경으로

**왜 이 프로젝트를 만들었나? → 연구 배경 및 필요성**

스스로에게 던져볼 세 가지 질문:
1. 이 프로젝트가 해결하려는 문제는 무엇인가?
2. 기존 방식(또는 유사 서비스)의 한계는 무엇인가?
3. 그래서 왜 새로운 접근이 필요했는가?

### 프로젝트 요소 → 논문 섹션 매핑

| 프로젝트 요소 | 논문 섹션 |
|---|---|
| 기획 & 설계 (동기·요구사항) | 서론 — 연구 배경 및 필요성 |
| 개발 & 구현 과정 | 방법 — 연구방법 및 설계 |
| 테스트 & 성능평가 | 결과 — 데이터와 성능 지표 |
| 아쉬운 점 & 개선 아이디어 | 논의 및 결론 — 한계와 향후 과제 |

### 서론 작성 예시

**❌ 이렇게 쓰면 약함**
> "본 프로젝트는 카페 예약 앱을 만든 것이다."

**✅ 이렇게 써보기**
> "기존 카페 예약 서비스는 실시간 좌석 현황을 반영하지 못해 이용자의 불편을 초래한다. 본 연구는 실시간 좌석 감지 시스템을 제안하여 이 문제를 해결하고자 한다."

무엇이 달라졌는가?
- '무엇을 만들었다'가 아니라 '어떤 문제가 있었다'로 시작
- 문제 → 해결 방향의 순서로 논증을 구성

### 방법·결과 작성 예시

**방법**
- ❌ "Python으로 여러 가지 기능을 만들었다."
- ✅ "Python 3.11과 Flask로 예약·알림·결제 3개 모듈을 구현하고, REST API로 연동했다."

**결과**
- ❌ "테스트해보니 잘 작동했다."
- ✅ "평균 응답시간 1.2초, 동시접속 200명 기준 오류율 0.3%로 측정되었다."

### 자주 하는 실수 네 가지
1. **스포일러식 서론** — 서론에서 결과나 결론을 먼저 말해버림
2. **근거 없는 자기 평가** — "이 프로젝트는 좋다"처럼 근거 없이 주장만 함
3. **코드 나열식 방법** — 왜 그 방법을 선택했는지 설명 없이 절차만 나열
4. **한계 언급 생략** — 완벽한 척하며 한계점을 아예 쓰지 않음

## Part 4. 형식과 연구윤리

### 인용 표기법 — 하나를 정해 끝까지

**IEEE 스타일**
- 본문: "…연구되었다[1]."
- 참고문헌: [1] 홍길동, "논문 제목," 학술지명, 2023.

**APA 스타일**
- 본문: "…연구되었다(홍, 2023)."
- 참고문헌: 홍길동. (2023). 논문 제목. 학술지명.

> 학과·지도교수가 지정한 양식을 처음부터 끝까지 통일해서 사용할 것.

### 표절 방지와 연구윤리

| 유형 | 설명 |
|---|---|
| 직접 표절 | 타인의 문장을 그대로 복사해서 씀 |
| 짜깁기 표절 | 여러 출처를 짜깁기하면서 출처 표기를 누락 |
| 자기 표절 | 이전에 제출한 과제·보고서를 그대로 재사용 |
| 데이터 조작 | 실험 결과를 임의로 수정하거나 과장 |

**예방법**: 인용 표시 + 참고문헌 등록 + 표절검사 프로그램 활용

### 그림·표·수식 작성 규칙
- 그림은 **하단**에 번호와 캡션을 붙인다 (예: "그림 1. 시스템 구성도")
- 표는 **상단**에 번호와 캡션을 붙인다
- 본문에서 반드시 한 번 이상 언급한다
- 화면 캡처를 그대로 쓰지 말고 필요한 부분만 편집한다

## Part 5. 글쓰기 실전 팁

- **짧고 명확한 문장**: 한 문장에는 하나의 주장만 담고, 능동태를 우선 사용
- **문단 간 논리적 연결**: 앞 문단의 결론이 다음 문단의 전제가 되도록 흐름 구성
- **초고 → 피드백 → 퇴고**: 혼자 완성하려 하지 말고 동료의 피드백을 받아 다듬기

### 문장 다듬기 실습

**❌ 약한 문장**
> "그리고 이 시스템은 여러 가지 좋은 기능들이 있어서 사용자들이 편리하게 잘 쓸 수 있을 것이라고 생각한다."

**✅ 다듬은 문장**
> "이 시스템은 예약, 알림, 결제 기능을 통합 제공하여 사용자 편의성을 높인다."

고칠 때 확인할 세 가지:
1. 불필요한 수식어를 제거했는가
2. 주어와 서술어가 호응하는가
3. "~것 같다" 같은 추측성 표현을 지양했는가
